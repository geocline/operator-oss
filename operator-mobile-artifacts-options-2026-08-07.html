Design options · August 7, 2026

One Operator URL for every useful artifact

The cleanest solution is to make artifact delivery a native Operator capability and improve the transcript in the same release. A second repository and server would duplicate authentication, navigation, storage, and uptime work that Operator already handles.

Recommended

Build a private, global Artifacts area inside Operator

Agents explicitly publish a finished file through a built-in tool. Operator snapshots it into durable storage, records its project and task, and immediately returns a stable phone-friendly URL. The Artifacts page lists everything newest-first and links each item back to its originating task.

Three approaches

A · Recommended

Native artifact registry

  • One existing Operator URL and login.
  • Explicit publishing prevents noisy app HTML from appearing.
  • Durable snapshot survives worktree cleanup.
  • Project and task provenance is automatic.
B

Separate artifact repository and server

  • Clear separation from Operator.
  • Adds another service, URL, authentication boundary, deployment, and failure point.
  • Must recreate task linking and metadata.
C

Automatic filesystem scanner

  • Requires no publish action.
  • Would collect build output, fixtures, dependencies, and unrelated HTML.
  • Files can disappear with worktrees and their intent is ambiguous.

Proposed publishing experience

Geo: “Publish that report”→ Agent calls publish_artifact→ Operator saves a durable copy→ Transcript shows Open + Copy link

The tool is automatically available to agents, so the remembered command is ordinary language: “Publish that artifact” or “Publish report.html.” When Geo explicitly asks for a deliverable to be published, the agent should not merely return a local filesystem link.

Global phone-first library

  • A memorable route such as /artifacts, accessible through the same private Operator hostname used on the phone.
  • Newest-first cards showing title, file type, publish time, project, task, and publisher.
  • Tap the title to open the artifact; tap the task tag to return to the exact Operator task.
  • Search by title, project, or task; simple type filters can be added without creating folders.
  • HTML opens in a constrained preview so an agent-generated document cannot control the Operator application itself.

Transcript improvements in the same release

  • No disappearing replies: every main-composer submission and every question-card answer becomes a permanent chronological “You” entry. Reloading must reproduce it exactly.
  • Timestamps: every user entry and assistant prose section shows its local time; older dates include the date as well.
  • Copy controls: every user or assistant message gets a Copy button, and every fenced code block gets its own Copy button. This covers links and prose even when the agent did not format them as code.
  • Mobile behavior: controls remain visible and finger-sized on touch devices; desktop can use quieter hover styling without hiding keyboard access.

Evidence from the current code

Already available: Operator is remotely reachable through its private hostname, runs persistent managed services, stores message timestamps in SQLite, and already recognizes HTML as a deliverable type.

Actual gaps: the transcript client currently drops stored message timestamps, question-card answers are rendered differently from normal user messages, Markdown has no copy controls, and there is no durable global artifact registry or browsing route.

Scope boundary

This first release should support explicitly published files, a global recent-first library, secure HTML viewing, task provenance, copying, durable user replies, and timestamps. Sharing artifacts publicly, editing them in-browser, automatic repository scanning, folders, and version comparison should wait until real use demonstrates a need.
