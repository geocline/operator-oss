Harness Model Admission and Operator Choices

Date: August 10, 2026
Status: Owner direction captured; awaiting Geo’s review of this written specification.

Goal: Adding a LiteLLM model to Operator must evaluate that exact model through Prime, Codex, and Claude Code where their protocols are compatible. Only harness-model pairs that pass are offered. LiteLLM remains a route/model source, never a user-facing harness.

User-facing taxonomy

The top-level Harness choice contains only real agent loops:

  • Claude Code
  • Codex
  • Prime Agent
  • Grok Build when implemented

Operator presents exactly three launch choices, in this order:

  1. Harness — Claude Code, Codex, Prime Agent, and later Grok Build.
  2. Model — one picker containing every model vetted for the selected harness. Models may be visually grouped as Anthropic, OpenAI/Codex, or LiteLLM, but there is no separate route or model-source control.
  3. Strength — only the reasoning levels supported by that exact harness-model pair.

LiteLLM is invisible routing infrastructure. The current litellm-codex driver may remain an internal adapter selected automatically when the chosen Codex model comes from LiteLLM, but “LiteLLM · Codex harness” disappears from the Harness picker.

Can Codex run other models?

Yes, when the model endpoint correctly implements the OpenAI Responses protocol and the model behaves correctly with Codex’s tool loop. To Geo this remains simply: Harness = Codex, Model = the selected vetted model. Internally, Operator automatically routes a LiteLLM-backed model through the existing Codex/LiteLLM adapter. Admission testing decides which models appear; HTTP compatibility alone is not enough.

Claude Code support

Add an internal litellm-claude adapter using an isolated Claude configuration and the LiteLLM Anthropic Messages-compatible route. Native Claude subscription sessions remain untouched. Only models that pass Claude Code tool-use, streaming, resume, stop, and output tests appear in the Claude Code Model picker. Geo does not choose the adapter or route.

Admission contract

A model’s operator.harnesses list is an output of vetting, not an unverified declaration. Admission records the exact alias, resolved physical model, harness, harness version, test revision, timestamp, and result.

GateRequired evidence
IdentityRequested LiteLLM alias and resolved physical model match policy; no fallback/substitution.
Basic turnModel returns a coherent assistant result through the exact harness transport.
Tool loopRead, edit, and command tools are called with valid schemas and paired results.
Operator bridgeAt least one scoped Operator tool succeeds through MCP/extension integration.
ResumeA second turn resumes the same harness session.
StopInterrupt settles the harness without leaving a busy process/session.
UsageTokens and metered cost are present or explicitly marked incomplete; absence never means free.
Repository resultA disposable fixture task produces the expected verified edit.

Catalog behavior

  • Prime shows every Operator-approved model whose admission record passes for prime.
  • Remove the hard-coded operator.kimi-k3 gate; replace it with the vetted Prime allowlist from the sanitized catalog.
  • Codex’s single Model picker shows native OpenAI models plus models that pass codex admission.
  • Claude Code’s single Model picker shows native Anthropic models plus models that pass claude admission.
  • A failed or stale admission removes only that harness-model pair. The model may remain available through another harness.
  • Refreshing the catalog never runs paid vetting implicitly. Vetting is an explicit operator command/action with visible results.

Recommended implementation order

  1. Make the compatibility result a first-class catalog type and enforce it in parsing.
  2. Generalize Prime from one hard-coded alias to all Prime-vetted aliases.
  3. Keep the existing Codex/LiteLLM adapter and run the admission suite against candidate models.
  4. Implement the Claude/LiteLLM adapter and run the same suite.
  5. Change the picker taxonomy to exactly Harness → Model → Strength. Resolve native versus LiteLLM adapters internally from the harness-model pair.

Testing

  • Parser tests reject claimed harnesses without passing admission metadata.
  • Prime policy tests accept all and only Prime-vetted aliases.
  • Codex and Claude adapter contract tests use deterministic fake CLIs/transports.
  • Live tests are opt-in and record immutable evidence without placing provider secrets in artifacts.
  • UI tests show only real harnesses, one model picker, and one strength picker; native/LiteLLM routing remains invisible.

Out of scope

This design does not claim every model will work through every harness. It creates the rule and evidence required to find out safely and honestly. Grok Build admission uses the same contract after its driver exists.
