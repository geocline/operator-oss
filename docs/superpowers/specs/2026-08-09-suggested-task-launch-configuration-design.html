Suggested Task Launch Configuration

Approved design for Operator's model-created subtask cards.

DateAugust 9, 2026 StatusApproved for implementation ScopeAgent-created suggested tasks; ordinary user-created tasks retain their current flow.

Outcome

A model-created task cannot start until Geo has reviewed and explicitly confirmed its Harness, Model, and Thinking strength. Operator suggests all three values, but suggestion is not confirmation. This removes the current start, interrupt, and handoff workaround.

User flow

  1. An agent creates a suggested task. Operator records that launch confirmation is required.
  2. The card shows a Review setup action instead of an enabled Start action.
  3. Edit opens with suggested Harness, Model, and Thinking strength values already selected.
  4. Geo may change any value, then selects Confirm setup.
  5. The saved card shows the confirmed configuration summary and enables Start.
  6. Changing Harness, Model, or Thinking strength before the first run clears confirmation and requires it again.
  7. Using Add moves the suggestion into the normal task list without bypassing the requirement. Its task hero continues to show Review setup until confirmed.

Terminology

UI labelInternal meaning
HarnessThe task's registered Operator agent/driver route, such as Claude Code, Codex, or LiteLLM through the Codex harness.
ModelThe explicit model alias saved on the task.
Thinking strengthThe task's reasoning preset. Supporting text may name the technical term, “reasoning effort.”

Suggested-value rules

  • Harness begins with the task's existing agent, which already inherits the project's default when the agent creates the suggestion.
  • Model begins with the task's explicit model when valid; otherwise Operator uses the first recommended model exposed by that harness.
  • Thinking strength begins with the task's explicit preset, then the agent-scoped app default when valid, then the balanced preset (think) when available, then the first supported option.
  • Changing Harness refreshes the Model and Thinking strength suggestions to valid values for the new harness.
  • Only reasoning choices supported by the selected model are shown when the capability catalog provides model-specific limits.

Durable state and enforcement

Two task fields distinguish launch requirements from confirmation: launch_config_required and launch_config_confirmed_at. Suggested tasks are created with required = 1 and confirmed = 0. Ordinary tasks are created with required = 0. Existing unstarted rows still in the Suggested tray are backfilled as required during schema migration.

Confirmation is an explicit API action, not a client-only checkbox. The server validates that the selected harness exists and that explicit Model and Thinking strength values are supported before recording the timestamp. Any pre-start change to those three settings clears the timestamp unless the same request explicitly reconfirms the complete configuration.

Server boundary: The initial-message endpoint rejects an unconfirmed required task before creating a worktree, message, or running turn. UI gating therefore cannot be bypassed by stale tabs or direct requests.

Error handling

  • If a harness is disconnected, confirmation may be saved, but Start remains unavailable until it is connected.
  • If a model disappears from a refreshed catalog, the task becomes unconfirmed and must be reviewed again.
  • If a selected harness exposes no models or no reasoning choices, the modal explains the missing capability instead of offering a false confirmation.
  • Failed saves preserve every edit and leave the modal open, using the existing bounded task-save behavior.

Compatibility

  • Already-started sessions and handoffs are unchanged.
  • User-created tasks are not retroactively gated.
  • The direct Add action does not clear launch requirements.
  • The existing task fields agent, model, and reasoning remain the execution source of truth.

Verification

  • Store and migration tests for new and existing suggested tasks.
  • API tests for confirmation validation, invalidated confirmation, and blocked initial launch.
  • Modal tests for suggested defaults, harness-dependent options, explicit confirmation, save retry, and preserved edits.
  • List and board tests proving Review setup replaces Start until confirmation.
  • Full test, typecheck, and production-build verification.
