Session Workspace and Agent Access Controls

Date: August 10, 2026
Status: Approved interaction design; awaiting Geo’s review of this written specification.

Goal: Every new Operator session starts visibly and intentionally in the project folder with full agent power. Workspace location and agent access are independent choices, editable from the mobile New/Edit session sheet before the first turn.

Product behavior

ControlDefaultAlternativesMeaning
WorkspaceProject folderIsolated worktreeControls the exact working directory where the harness reads and edits files. It does not change tool permissions.
Agent accessFull powerHarness-supported restricted modesControls tool/command permissions. It does not change the working directory.

The controls appear as two compact rows in an Execution section. Each row shows the effective choice and uses a native mobile-friendly select. A one-line summary states the exact outcome, for example: “Runs directly in /Users/geo/Claude Projects/operator with unrestricted harness permissions.”

Where the controls appear

  • New task: visible before “Start session immediately,” so a task cannot start with hidden defaults.
  • Edit task: visible for every task before its first turn, not only agent-suggested tasks.
  • Started task: workspace becomes immutable because moving a live session to another directory breaks resume semantics. Agent access remains adjustable for later turns through the existing session control and Edit task.

Persistence and migration

Add tasks.workspace_mode with values direct and worktree. New tasks created through Operator persist direct. The project-level run_in_repo setting no longer silently determines a task’s location; it can remain as a legacy/project-default setting during migration, but every task stores its own explicit choice.

Migration preserves active work:

  • Tasks with a nonempty worktree_path backfill to worktree.
  • Tasks without a worktree backfill to direct.
  • No existing worktree is moved or deleted.

New tasks explicitly persist permission_mode = "bypassPermissions", so an unrelated app-level default cannot quietly turn a new full-power session into plan/restricted mode.

Plain-language rule: “Full power” must mean the strongest mode the chosen harness actually supports. Operator must not label Codex workspace-write as full power.

Server enforcement

  • The task creation API validates and persists both controls.
  • The task patch API allows workspace_mode changes only while started = 0 and no worktree exists.
  • The first-message route creates a worktree only when workspace_mode = "worktree"; otherwise it leaves worktree_path empty and the driver receives project.repo_path.
  • Invalid workspace or permission values fail closed with a readable 400 response.
  • Changing harness before the first turn revalidates the selected access mode; unsupported modes reset visibly to Full power rather than producing a broken launch.

Testing

  • Database migration and backfill tests.
  • Task creation defaults: direct + explicit full power.
  • First-message tests proving direct mode never creates a worktree and worktree mode does.
  • API tests proving workspace cannot change after start.
  • Driver tests proving Codex Full power uses danger-full-access.
  • Mobile component tests proving both controls render, remain independent, persist their selections, and show the correct summary.

Out of scope

This feature does not add Grok Build, change model routing, delete existing worktrees, or redesign the entire task modal. It changes the execution controls and their runtime truth only.
