Everything below is one idea wearing different hats: your work lives in a few places at once, and each command moves it from one place to the next. Nothing here is exotic. Most of it is filing.

1

The four places your work lives

Read this left to right. Work starts on your machine and only becomes shared at the last step. Each arrow is the command that pushes it one box to the right.

Place 1

Your folder

The actual files, right now. Edit, save, break, fix. Nobody sees this but you.

→git add

Place 2

The staging pile

The changes you have selected to save. A waiting room, so one save can hold 3 files and ignore 5 others.

→git commit

Place 3

History, on your machine

A permanent, labeled snapshot with a message. Still 100% private. This is your undo point.

→git push

Place 4

GitHub, shared

The copy other people (and other machines) can see. This is the moment work becomes public to your team.

← Coming back the other way: git pull brings other people's commits down into your folder. git clone is just the very first pull, when you have nothing yet.
So what is a commit? A commit is a dated, labeled snapshot of the project filed into its history, on your computer only. It publishes nothing. It emails nobody. It is the thing that lets you say "put it back the way it was on Tuesday" and actually get it. Committing often is free. Not committing is what costs you.
And a push? Push takes the commits you already made and uploads them to GitHub. That is the step with social consequences, which is why I never commit or push for you unless you say so in that message.
2

The words, translated

WordWhat it actually meansWhen you hear it
diffThe list of exactly what changed, line by line."Check the diff" = look at what I changed before you accept it. Red lines were removed, green lines were added.
commitSave a labeled snapshot into local history.Also used as a noun: "that commit broke it" means that one snapshot.
commit messageThe label on the snapshot.Good ones say why, not what. The diff already says what.
branchA separate line of work, started from a copy of the main one."main" is the trunk, the real version. A branch is a side track you can abandon with no damage.
mergeFold one branch's commits back into another.The moment side work becomes real work.
conflictTwo branches changed the same lines, so git refuses to guess.Not a disaster. Somebody (or an agent) picks the right result and the merge continues.
pushUpload your commits to GitHub.Your work is now visible to everyone with access.
pullDownload everyone else's commits into your copy.Do it before starting something big, so you build on current code.
remote / originThe shared copy on GitHub. "origin" is just its nickname."push to origin" = send it to GitHub.
pull request (PR)A formal "please review my branch and merge it" on GitHub.A discussion page wrapped around a diff. Nothing merges until someone approves.
worktreeA second folder holding the same project, on its own branch.Lets two people or two agents work at once without stepping on each other. See section 3.
stashA temporary shelf for half-done work.Used to get your desk clear for five minutes, then put back.
revertA new commit that undoes an old one.The safe undo. History keeps both, so the record stays honest.
reset --hardThrow uncommitted work away, permanently.The unsafe undo. There is no bin to fish it out of.
HEAD"Where you are standing right now" in the history.Mostly appears in error messages. Usually means the latest commit on your branch.
3

Trees: two desks, one project

A worktree is a second checkout of the same repository, in its own folder, on its own branch. Same project, same history, separate files. That is the entire trick, and it is what makes it safe to run several agents on one codebase at the same time.

Operator default

Project folder

Called "direct". The agent edits your real repository.

  • Changes appear in your editor immediately.
  • No branch, no diff tab, no merge step. It is simply done.
  • Undo is ordinary git: revert the file, or reset it.
  • Pick this when you asked for something and you want it done.
Opt in per task

Isolated worktree

A private copy under ~/.agent-orchestrator/worktrees.

  • Your repo stays untouched until you press merge.
  • The task's DIFF tab shows exactly what it did.
  • Deleting the task throws the work away cleanly.
  • Pick this for parallel tasks, risky rewrites, or anything you may bin.
  your project (main)
  |
  |__ ~/Claude Projects/operator          <- the real thing. "Project folder" tasks edit this.
  |
  |__ ~/.agent-orchestrator/worktrees/ab12  <- task A's own copy, branch task/ab12
  |
  |__ ~/.agent-orchestrator/worktrees/cd34  <- task B's own copy, branch task/cd34
                                          merge lands these back into main
The one rule that matters Two "Project folder" tasks running at the same time in the same project share one set of files, and nothing stops them overwriting each other. Rule of thumb: one direct session per project at a time. Anything running alongside it should be an isolated worktree.
Fixed at launch A task's workspace cannot change once its session starts, because its files and branch already exist. If you picked wrong, make a new task. Existing worktree tasks were migrated as they were and behave exactly as before.
4

What the Operator buttons really do

Workspace: Project folder

= no worktree, edit in place

The agent's cwd is your repo. What it writes is what you have.

Workspace: Isolated worktree

= git worktree add + new branch

Created on the task's first message, from your project's base branch.

DIFF tab

= git diff

Only shown for worktree tasks. Direct tasks have nothing pending to show.

Merge

= git merge into your base branch

Takes the task's branch and folds it into the project. Conflicts can be handed back to the agent to resolve.

Sync / "caught up to main"

= git pull, but only when trivial

Before a follow-up turn, a clean worktree is fast-forwarded onto the base branch so the agent builds on current code.

Agent access: Full power

= no approval prompts

The agent runs commands and edits without asking. Plan mode is the read-only opposite: it proposes and touches nothing.

5

How scared to be

Free
Do it often
commit, branch, diff, stash, making a worktree. All local, all reversible. A commit is the cheapest insurance in software. Committing before you try something is how you make trying something safe.
Visible
Think first
push, merge, opening a PR. Now other people see it or depend on it. Still fixable, but fixing it happens in public and someone may have already pulled your work.
Sharp
Ask first
reset --hard throws away uncommitted work with no recovery. push --force rewrites shared history and can delete a colleague's commits. Deleting a task in Operator is a hard delete: no undo, no bin.
6

The five you would ever type

CommandReads as
git status"What have I changed, and what is waiting to be saved?" Always safe. Start here when lost.
git diff"Show me the actual edits." Always safe.
git log --oneline"Show me the last snapshots and their labels."
git checkout -- ."Throw away my unsaved edits and go back to the last commit." Sharp: it is a real delete.
git push"Send my commits to GitHub."
Honestly though You do not need to type any of these. Ask in plain words: "what changed?", "save this with a message about why", "put it back the way it was this morning". The words in this sheet exist so that when the answer comes back mentioning a commit or a branch, you know exactly which of the four places is being talked about.
Standing rule Nothing gets committed or pushed on your behalf unless you ask for it in that message. Approving it once does not approve it next time.
