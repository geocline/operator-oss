## Diagnosis

The regression was introduced by commit `54500cf` ("test fixture: seed transcript timestamp regression"), which touched three spots:

1. **`app/orchestrator/Transcript.tsx` — `MessageView` header**: the `<MessageTime>` element was moved from the *leading* position in the `.who` header to the trailing meta position (after the spacer), and rendered **unconditionally** — so assistant continuation rows (`hideWho`) also got timestamps, and user prompts / first replies no longer led with the time.
2. **`app/orchestrator/Transcript.tsx` — `isFirstAssistantReply` deleted**, and **`SessionView.tsx`** fell back to a naive `prev.role === "assistant" || "tool"` check. Because a reply can legitimately begin with tool calls before the first prose, the first assistant prose after leading tool activity was misclassified as a continuation and lost its header/timestamp entirely.
3. **`ArtifactNoticeView`** (a system-notice row) *gained* a `<MessageTime>`, violating the rule that non-conversational rows get no timestamp. The `.msg-time` CSS was also restyled for the trailing position.

## Fix (smallest correct change)

Reverted the seed commit — restoring the previously-working implementation, no test edits:

- Restored `isFirstAssistantReply(messages, index)` in `Transcript.tsx`: walks backwards from an assistant message, tolerating tool rows, and returns true at the first user prompt.
- `SessionView.tsx` computes `hideWho = m.role === "assistant" && !isFirstAssistantReply(...)` again.
- `MessageView` renders `<MessageTime>` **first** in the `.who` header, only when the header is shown (`!hideWho`); queued user messages also lead with their time.
- Removed the timestamp from the artifact-notice (system) row and restored the badge-style `.msg-time` CSS for the leading position.
