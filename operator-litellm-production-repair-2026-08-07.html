Incident report · August 7, 2026

Operator × LiteLLM production repair

The screenshot was a real production failure, and the prior testing did not exercise the transport Operator uses in a normal Codex-harness task. This repair was validated through the running app with all three paid model routes.

Repaired and live-tested

What failed

502 Bad Gateway

Codex opened /v1/responses as a WebSocket. Operator’s credential-hiding relay handled ordinary HTTP only, so the upgrade request failed.

Missing metadata

Aliases such as operator.deepseek-v4-pro are intentionally dynamic, so they are not present in Codex’s built-in model catalog.

Testing gap

The earlier smoke path used HTTP and did not reproduce a normal/default Codex turn. It therefore missed the exact route visible in the screenshot.

The production path now

Operator

Loads only models currently tagged for Operator in LiteLLM.

→

Codex harness

Uses a dedicated custom provider with WebSockets disabled for this route only.

→

Local relay → LiteLLM

HTTPS streaming; the child sees only a loopback credential. The real gateway key remains hidden.

What changed

Clean HTTPS transport

LiteLLM’s Codex provider now advertises supports_websockets = false. Codex uses streaming HTTPS immediately instead of retrying a WebSocket five times.

Dynamic model metadata

Operator generates a private Codex catalog from the refreshed LiteLLM catalog. New tagged aliases appear without an Operator code change.

Credential boundary preserved

OpenRouter credentials remain in LiteLLM. Operator’s Codex child receives only the short-lived loopback relay credential.
